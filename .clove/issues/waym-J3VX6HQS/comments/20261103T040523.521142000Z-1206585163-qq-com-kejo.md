Resolution: the write lock's lifecycle is settled as follows.

**Primitive and location.** The project write lock is one store-wide OS advisory exclusive lock (`flock`/`fcntl` on Unix) on a dedicated regular file at `<project>/.waymark/write.lock`. It is never taken on a work-item file, because work-item files are replaced by temp+rename and an advisory lock on one binds to an inode that is no longer the item's path. The lock file is created by the first mediated write, is listed in `.waymark/.gitignore` (a missing entry is repaired on the next acquisition), and is opened without following a symlink, so a cloned repository cannot turn it into a link to a user file. Its content is never read or written; it carries no holder metadata. The kernel releases the lock on process exit or crash, so there is no stale-lock reclamation, no PID probe, and no mtime expiry.

**Coverage.** Every mediated write takes this one lock — work items, relationships, archive, migration, and configuration edits. Reads, `show`, dry-runs, and previews are exempt and never block on it. A global read builds its projection and detects a concurrent multi-file write through its inventory/fingerprint check, retries a bounded number of times, then returns a retryable error rather than a torn snapshot.

**Granularity and reentrancy.** One public operation acquires the lock exactly once and holds it through prevalidation, every write it stages, and rollback. Internal helpers that write receive the held guard instead of acquiring again; nested acquisition is a programming error, never a blocking wait. Long-lived adapters (MCP server, Web) never hold the lock between calls.

**Waiting.** A writer waits a bounded time, 10 seconds by default, configurable per project and overridable per operation through a shared option that both CLI and MCP expose (`0` means fail immediately). On expiry it returns a retryable structured error naming the lock path and waited duration and guaranteeing that nothing was written; no holder identity is exposed.

**Failure taxonomy boundary.** Three concurrency conditions stay distinct: lock contention (retryable, zero writes), a fingerprint conflict with an external edit (terminal; the caller must reread and re-derive the change), and reader snapshot instability under a concurrent multi-file write (retryable, read-only). The final code names are fixed by the error-taxonomy ticket.

**Diagnostics and failures.** Failing to open or take the lock file (unreadable path, read-only project directory, a non-regular file) is a terminal operation error; reads still work in a read-only checkout because they never need the lock. `doctor` probes the lock with a non-blocking try-lock and, when it is held, reports a non-fixable informational finding that a mediated write is in progress — it never waits and reports no holder identity.

**Platform and filesystem.** v1 targets Unix (Linux and macOS); advisory locking, `O_NOFOLLOW`, and temp+rename replacement are specified against POSIX semantics, and Windows is explicitly out of scope. The lock is supported on local filesystems only; concurrent access over NFS/SMB is not supported. The lock's lifetime follows the project metadata directory, not the storage root; storage migration never moves or recreates it.
