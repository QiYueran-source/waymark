Resolution: Configuration and migration split on one mechanical rule — a configuration operation never reads or rewrites work-item files; any operation that must touch them is a migration. Configuration therefore covers operator, project time zone, cache settings, category display names, adding an optional custom field, and field metadata that only loosens constraints. Storage root, category path, category key, custom-field removal, and adding a required field are migrations.

Naming: `config` and `migrate` stay separate verb namespaces that share the object vocabulary `category` and `field`, so the same nouns read consistently in both while a command's safety class is visible from its verb. No command under `config` ever moves or rewrites a work item. Configuration forms are `config set <scalar> <value>` for operator, timezone and `cache.*`, plus `config add|set|remove category` and `config add|set field`. Migration forms are `migrate storage --root|--category-path|--category-key` and `migrate schema --remove-field|--add-required-field`.

Categories: adding a category, changing its display name, and removing it are configuration; changing its path or key are storage migrations. A category may be removed only when no work item references it, archived items included; otherwise the call returns `CATEGORY_IN_USE` and the caller must move items first. Item reassignment is never automatic, because rewriting `category` is a migration, not configuration cleanup.

Custom fields: adding an optional field is configuration, since existing items are simply unset. Adding a required field is a schema migration that backfills the declared static default into every existing work item. Direct field-metadata changes are limited to description/display name, static default, and `required: true → false`; `required: false → true`, type changes, key renames, and list element-type changes are rejected.

Locking and projection: configuration writes that touch only the configuration file take the project lock and check that file's fingerprint, but do not require a complete work-item projection. Configuration writes that must check references — category removal — require a complete fresh projection.

Storage relocation mechanics: a category path change is a directory-level relocation, not N file edits, because a category directory holds only `<stable-id>.md` files and no subdirectories. Same-filesystem relocation is a single directory rename. Cross-filesystem relocation degrades to creating the target, copying each file, verifying fingerprints, and then deleting the sources. Pure relocations leave file contents and fingerprints unchanged and do not update `updated_at`; category-key relocation additionally rewrites the `category` value in every affected file and therefore does update `updated_at`. A failure moves already-relocated directories back, and reports `rollback_failed` with the paths that moved when it cannot.
