## Goal

Define how Waymark is built, packaged, and released: the basic versus Web-enabled variants, the formal `waymark serve` entry point, embedded frontend assets, artifact names, version reporting, and release automation. This map holds the decisions; its specification and implementation tickets are cut after the decisions settle.

## Context

The functional specification and the Web implementation deliberately stop at a development/test launcher. Formal `waymark serve`, the optional Web feature, embedded release assets, installation, packaging, downloads, and release automation are separate work that must reuse the existing server and frontend build output rather than building a second implementation.

## Decisions so far

- The basic distribution includes CLI, the shared core, and MCP; Web is optional. A build-time feature selects Web: the default build is the basic version, while a Web-enabled build includes Web. Adding Web to an installed basic executable requires rebuilding or installing a Web-enabled replacement, not dynamically attaching a module.
- The basic CLI retains `waymark serve` but reports clearly that Web is not included and directs the user to install a Web-enabled build; it never downloads or installs anything automatically.
- A Web-enabled build must obtain complete frontend assets. Missing assets or a frontend build failure must produce a clear build failure, rather than silently shipping a placeholder or stale frontend as a successful Web build.
- A prebuilt Web-enabled binary includes its frontend assets; an end user running it does not need Rust, Node.js, or npm. To build the frontend from source, the developer needs Node.js and npm unless verified prebuilt assets are supplied instead.
- Formal releases provide separately named prebuilt basic and Web-enabled binary packages. Both identify their version and included capabilities; the basic package includes CLI and MCP without Web, and the Web package includes those capabilities plus Web.
- Building Web from a Git checkout uses Node.js/npm and the frontend lockfile to install dependencies and build assets; failure fails the Web build. The published Web source package includes prebuilt frontend assets, avoiding a GitHub Release download at build time. These assets must correspond to the source version and release checks must validate that correspondence; the exact verification mechanism is open. Both paths embed assets in the resulting binary; Web runtime requires no Node.js/npm.
- The first Web version listens only on local loopback addresses and offers no LAN or public binding; Host/Origin rules, safe Markdown rendering, and read-only behaviour are already settled in the functional specification and Web specification.
- T12 supplies only a development/test launcher. Formal `waymark serve`, CLI feature gating, and embedding release assets belong to this distribution work and reuse T12's server and frontend build output.
- **Release pipeline:** one GitHub Actions workflow runs on `v*` tags, builds every artifact, and attaches them to a **draft** Release; a human runs the release checks and publishes the draft. The repository has no CI today, so this is its first pipeline. Clove's tag-triggered draft-release flow is the reference; its automatic `cargo publish` stage is not adopted (see below).
- **Build variant:** `waymark-cli` gains an off-by-default `web` feature (`web = ["dep:waymark-web"]`); `waymark-web` is an optional dependency, so a basic build does not compile it and cannot reach frontend assets at all. Asset embedding and the real `serve` implementation live behind that feature. There is no `full` alias: one optional capability does not need an aggregate feature.
- **`waymark serve` presence:** the command exists in both builds. Without the `web` feature it reports that Web is not included and points to the Web package; with the feature it serves. It never downloads or installs anything automatically.
- **Platforms:** linux x86_64 (gnu), macOS aarch64, and macOS x86_64. Windows x86_64 is a first-class target delivered by [Waymark Windows platform support](wm-vfbqmw1r7x0j); the pipeline specified here gains the Windows artifacts when that specification is implemented.
- **Artifacts:** `waymark-v<version>-<os>-<arch>.tar.gz` (basic) and `waymark-web-v<version>-<os>-<arch>.tar.gz` (Web), `.zip` on Windows, each with a `.sha256` sibling. An archive holds `waymark` and `waymark-mcp` (`waymark.exe`, `waymark-mcp.exe` on Windows), `README.md`, `LICENSE-MIT`, `LICENSE-APACHE`, and `THIRD_PARTY_LICENSES.txt` generated by cargo-about. The Web package keeps the `waymark` binary name; the variant is a package-level distinction, not a command-level one.
- **Versioning:** the workspace declares one version; the release tag must equal it or the workflow fails; both variants share the version and tag. `-rc.N` pre-releases are allowed; `master` does not carry a permanent `-dev` suffix — the version is bumped in the release commit and tagged immediately after.
- **No crates.io publishing:** a release is a GitHub Release plus a source tarball attached to it that carries the prebuilt frontend assets. "Published Web source package" means that Release tarball, not a crates.io crate; Waymark has no library consumers to justify crates.io's irreversible publish and per-crate verify builds.
- **Release notes:** a hand-written `CHANGELOG.md` (Keep a Changelog) is the source of truth; the workflow only produces a GitHub draft via `generate_release_notes`, which a human edits to match the changelog before publishing. No release-plz or generated-changelog tooling in v1.
- **Integrity:** SHA-256 checksums plus a cargo-about dependency-licence inventory. No binary signing, no Apple notarization, and no SBOM in v1; the macOS Gatekeeper consequence for unsigned binaries is documented in the install guidance rather than ignored.
- **Frontend provenance:** the frontend build emits `assets-manifest.json` (file list, per-file SHA-256, build id); the build embeds it in the binary, and `waymark version --json` exposes it. Release checks assert the manifest version equals the tag, that `index.html`'s hash matches the manifest, and start the packaged Web binary, fetch `/`, and compare the served hash. A mismatch fails the build with `ASSETS_VERSION_MISMATCH`; at runtime `waymark doctor` reports it as unhealthy without blocking startup.
- **Release gates:** a release requires `cargo fmt --all --check`, `cargo clippy --workspace --all-targets --all-features -- -D warnings`, `cargo test --workspace --all-features` green on Linux and macOS, the frontend `npm ci && npm run check && npm run build`, and a real Rust 1.85 toolchain build — all green on the tagged commit. Windows gates belong to the Windows specification.
- **Windows support:** specified separately as [Waymark Windows platform support](wm-vfbqmw1r7x0j): one target, `x86_64-pc-windows-msvc`, `.zip` artifacts, portable fallbacks for the two Unix-only checks, and a `windows-latest` job in pull-request CI. The shared pipeline here does not ship Windows artifacts until that specification is implemented.
- **`waymark serve` surface:** `waymark serve [--project DIR] [--port PORT] [--open]`, default port `7331` (the Web crate's `DEFAULT_PORT`), binding `127.0.0.1` only. It does not open a browser unless `--open` is given. A busy port reports `PORT_IN_USE` and points at `--port 0` instead of silently choosing a free port — a deliberate divergence from Clove, which falls back and only prints a note. Readiness prints `serving http://127.0.0.1:<port>`; with `--json` it emits `{"url": …}` and keeps running.
- **Installation and MCP guidance:** the README carries an Install section (download, extract, verify SHA-256, the macOS Gatekeeper note for an unsigned binary, and replacing the binary to move from basic to Web without touching `.waymark/`), and `docs/mcp-clients.md` carries Claude Code, DSH, and generic stdio configuration examples. v1 ships no install script and no Homebrew or other package-manager tap.

## Not yet specified

None. The frontier is clear: what remains is execution detail for the distribution specification, not a decision.

## Out of scope

- Web UI behaviour, MCP business behaviour, and any new product feature.
- Building a second Web server or frontend.
- LAN or public network binding.
- Non-loopback deployment.
- Windows ARM64 and non-MSVC Windows toolchains.
