## Destination

Produce a handoff-ready functional specification for Waymark, a general-purpose, Git-friendly work-item tracker with configurable storage and project-level custom fields. This map resolves remaining product and domain decisions; it does not implement Waymark.

## Notes

- Use Clove as this repository's issue tracker.
- Treat Clove as a behavioral reference, not a required feature checklist.
- Keep categories and project workflow conventions configurable; do not build Wayfinder-specific semantics into Waymark's core.
- Consult the grilling and domain-modeling skills for decision tickets.
- The earlier functional specification and its implementation tickets are retired: the specification is archived at `.inbox/WAYMARK-FUNCTIONAL-SPEC.md` and the tickets were closed with a supersession comment. The CLI/MCP interface working document moved to `.inbox/superpower/` once its settled content was absorbed. The consolidated record is [Waymark functional specification](wm-srxj8ztv1zfz), which carries the full settled contract plus a Not yet specified section; that issue is the buildable artifact, this map remains the decision record. Do not implement Waymark from the retired documents.
- Documentation topology after acceptance: this map closes and stays as decision history; `GLOSSARY.md` carries the storage and machine-contract vocabulary the specification relies on; `docs/adr/` records the three decisions whose reversal would be expensive — archive irreversibility, the single kernel-released write lock, and recovery-unit error codes. Implementation tickets are cut from the specification, not from this map.

## Decisions so far

- [Define Waymark command and integration surface](wm-cc9kg5t2cvtb): Core domain operations live in a shared function library; CLI and MCP are adapters, frontier-specific semantics stay outside the generic tracker, and general leaf/tree queries are in scope.
- [Define issue lifecycle, archive/delete, and reference integrity](wm-a9ta88cr141f): Archive is irreversible through Waymark and acts as logical deletion; the original file remains, archive metadata is added in frontmatter, active children block archiving, and Waymark clears recognized inbound core relationships in one safe batch without touching body/custom-field references.
- [Define owner transfer, operator guardrails, and write authorization semantics](wm-hywz3afj7pr1): Create may assign another human owner; transfers take effect immediately; batches are all-or-nothing; identities are not authenticated. Its write-gate portion is superseded: the operator/owner check is now advisory only (see below).
- [Define project-level custom field types and schema syntax](wm-wr11be4s3vpd): Custom fields use basic shape types only (string, integer, boolean, homogeneous list); enum is a string convention, fields are optional by default, and custom values have no reference/workflow behavior.
- [Define generic custom-field filtering and projection semantics](wm-2qd0yahgpa8t): A finite generic query set supports presence, equality, typed comparisons and string matching; list membership is explicit; null is disallowed; sorting and projection have deterministic missing-value behavior, with strict type errors.
- [Define configuration and frontmatter evolution and migration policy](wm-ahdybfq7rwkv): Established that one command-managed version governs configuration and work-item compatibility, that incompatible changes require explicit dry-runnable prevalidation, that serialization is deterministic, that future or invalid data is rejected, and that archive metadata lives in work-item frontmatter. Its migration mechanics — durable backups and lazy upgrade on normal write — are superseded by "Resolved migration and versioning semantics" below.
- [Define file concurrency and index behavior](wm-10v2zrdpknqg): Work-item files are the sole authority; Waymark does not persist a JSON index. A complete in-process static frontmatter projection is rebuilt or incrementally synchronized from files, with explicit completeness/freshness states, project-level locking, fingerprint conflict checks, and application-level batch rollback.
- [Define read-only Web tree overview and navigation](wm-djw788wb4606): Web is a strictly read-only visual overview with combined/category-grouped trees, category shape cues, work-state colors, optional dashed dependency overlays, simple details/navigation, and browser-local view-state persistence; archived items are excluded by default. Follow-up decisions from 2026-11-04: combined remains one cross-category hierarchy with category identity cues on nodes; category-grouped view offers category selection buttons; when filtering, an unselected-category ancestor required to preserve the selected item's real hierarchy remains as temporary context and must be prominently marked as outside the selection. A graph visualization is desired as an additional view alongside the tree. It uses parent-child edges as solid edges by default and, when the existing dependency visibility toggle is enabled, renders dependency edges as dashed lines; no other relationship types are shown. Use a hierarchical layout (top-to-bottom or left-to-right) to preserve the parent-child reading order rather than a force-directed layout. Category selection filters the graph the same way as the grouped tree, retaining any unselected-category ancestor needed to preserve selected nodes' actual parent context and prominently marking it as temporary context. These graph-view behavior decisions were confirmed by the user on 2026-11-04. Category filtering is multi-select and provides select-all and clear-all actions; required unselected-category ancestors remain prominently marked temporary context. The graph initially displays the complete parent-child hierarchy and fits it to the viewport on first entry; provide per-node collapse/expand controls to manage density in large projects. Clearing all categories or selecting categories with no matching items shows an explicit empty state with a way to select all categories. Archived items are excluded entirely and are treated as deleted for graph display; they are not shown as nodes, unresolved entries, or explicit placeholders. Other unresolved parent cases (missing parent or parent cycle) remain in a dedicated unresolved-relations area with their reason shown, without inventing a parent node or treating them as ordinary roots. Graph node collapse/expand state is persisted per project and separately from tree expansion state, ignoring IDs no longer present after data changes. The graph retains an accessible structured text/list alternative that users can toggle, so keyboard and screen-reader users can read nodes, parent-child relationships, dependency relationships, and unresolved reasons without relying on visual edges. Dependency edges are directional and use arrowheads; include a concise legend defining solid edges as parent-child and dashed edges as dependencies. These accessibility and edge-legend decisions were confirmed by the user on 2026-11-04. The graph uses a fixed top-to-bottom hierarchical layout; selecting a node opens the existing read-only item detail, visibly marks the selected node, and never permits dragging nodes to mutate relations. Provide canvas pan, zoom, fit-to-view and reset-viewport controls, with touch/trackpad gestures supported. Persist graph viewport state separately from tree state per project in browser storage; if storage is unavailable, graph controls continue to work for the session without persistence.
- [Define Waymark delivery scope, archiving UI, and history capabilities](wm-wzhng69e7chj): No separate archive browser, no delivery-phase commitments, no import/export or separate audit log; Git provides history/diff, and the resolved tree overview is the complete Web scope. Explicit archive-aware CLI/MCP queries remain available; Web stays read-only and excludes archived items.
- [Define the query and reporting surface](wm-b34p3ccasdjd): Waymark adopts Clove's read skeleton (list/ready/blocked/query/search/show/stats/tree/dep tree) with its own field vocabulary; list, ready and blocked share one filter set; default `rank` ordering is status group, then dependency topology, then id; `stats` reports counts only, with no history or throughput.
- [Define creation defaults and required inputs](wm-vx6w5s4m9mqh): `create` requires title, category, and owner with no derivation; `creator` is optional immutable provenance that may stay unset; a missing required custom field fails the whole create; initial relations turn a scoped create into a complete-projection create.
- [Define the configuration command surface and its migration boundary](wm-2gc9r3qmthc4): Configuration never reads or rewrites work-item files, and anything that must is a migration; `config` and `migrate` keep separate verbs over shared `category`/`field` nouns; category path and key changes relocate directories rather than editing files, with pure relocations leaving contents, fingerprints and `updated_at` untouched.
- [Define concurrency and lock lifecycle](wm-r2ddh3jgka17): One store-wide advisory lock on `.waymark/write.lock` releases through the kernel (no stale reclamation), is acquired once per mediated write and never reentrant, covers configuration and migration too, leaves reads lock-free, and waits a bounded 10 seconds by default before a retryable timeout.
- [Freeze the error taxonomy and exit-code mapping](wm-163w6b1mb6gd): One shared registry pins every code's exit class, retryability, typed details and location kinds, and doubles as the diagnostic vocabulary; codes are coarse recovery units rather than error variants, class 4 is narrowed to conflict and state rejection, warnings never change the exit code, and compile-time exhaustiveness plus a golden snapshot make adding a code deliberate.
- Stable IDs are independent of category, name, and path; storage root and category paths are configurable. Configuration includes a project time zone for human-readable time output and parsing local time inputs without offsets; persisted timestamps remain UTC RFC 3339, offset-bearing inputs retain their instant, and changing the time zone never rewrites work-item files. Ordinary operations cannot accept caller-forged system timestamps; a future explicit historical migration/import path may convert legacy times.
- Categories are project-defined groupings, without category-specific field schemas in the initial model.
- Parent is a single cross-category hierarchy edge; parent and hard dependencies are independent, and only dependencies block readiness. Parent lifecycle does not cascade to children.
- Core fields have stable meanings. Project custom fields are declared at project scope, uniquely named, optional by default, and do not implicitly alter core behavior. Executor is project-defined rather than a Waymark core field; generic field querying must be available.
- Creator is provenance; owner is required human accountability; owners must be human. Owner transfer is expected to be initiated by the current owner, but without an authenticated identity that expectation is surfaced as a warning rather than enforced.
- The configured operator is advisory. It names who is running a Waymark-mediated operation and produces a warning — never a refusal — when it differs from a work item's owner. It is a project configuration value, not a work-item field, and it is optional. Executor metadata does not grant write authorization.
- Clove's strict, predictable frontmatter is a format reference, but Clove itself has no custom-field schema/query support. Clove's unified edit path is the reference for full-body replacement, empty-body clearing, non-interactive `--body`/`--body-file` CLI modes, and structured MCP edits; Waymark v1 intentionally omits interactive editor support.
- Core-field decisions are resolved: the complete persisted v1 field set, `closed_at`, ID/category-key formats, identity/time normalization, frontmatter archive metadata, and computed `blocked`/`ready`/`blocked_by` fields with dangling-dependency diagnostics. `blocked` is not a lifecycle status; `blocked_by` is a read-only computed field and is never persisted.
- Index/cache decisions are resolved: documents are the sole authority; a complete in-process static frontmatter projection is derived from them; derived readiness and graph results are computed dynamically; local operations may use incomplete projections only when explicitly marked, while global queries and archive require completeness. A bounded LRU may cache body/details only, never evict relation nodes.
- `touch` is an internal term for a Waymark-controlled frontmatter query, frontmatter mutation, or archive; it is not a timestamp update and does not mean arbitrary body access. Public interfaces use explicit read/write/archive/sync names.
- [Define the replacement specification's shape](wm-9qwnw8wr9d2g): The replacement is a `/to-spec`-shaped implementation brief that lives in Clove, absorbs the interface working document, restates settled decisions instead of linking them, and keeps undecided areas visibly undecided.

### Resolved archive semantics

- Archive is an irreversible-through-Waymark logical deletion, not a lifecycle transition and not `closed`. It is allowed from `open`, `in_progress`, or `closed`; it does not change `status` or `closed_at`.
- Archive preserves the original Markdown file and all existing metadata, including body, custom fields, `parent`, `dependencies`, and `soft_links`. It adds `archived_at` and optional `archive_reason` in the same frontmatter, does not add `archived_by`, and does not update `updated_at`.
- Only the current owner may initiate archive, subject to the declared operator/owner process guardrail. Archive is a mediated write; archived items reject later edit, body, status, owner, transfer, and relationship writes.
- Re-archiving returns `ALREADY_ARCHIVED`, does not replace `archived_at` or `archive_reason`, and does not create another change.
- An item with any unarchived child is rejected with `HAS_ACTIVE_CHILDREN`. Archive never cascades to children; users must archive children individually, clear their parent, or move them first.
- Archive does not provide a Waymark restore/unarchive command. A user may manually restore a historical Git version; current frontmatter determines whether the item is active or archived.
- An archived item is excluded from active tree, list, search, ready, blocked, and stats results. `show <id>` can read it. `--archived` selects archived-only collections; it does not mix archived items back into the active graph.
- The archived item's own relationship fields remain as historical context and are shown as historical relations. They do not participate in active graph calculations. New relationships cannot target an archived item.
- Archive removes recognized inbound core relationships from active files: inbound `dependencies`, inbound `parent`, and inbound `soft_links`. It does not inspect or modify body mentions or custom-field values. Affected active files update `updated_at`; the archived target does not.
- Archive requires a complete fresh project projection, performs full prevalidation under the project lock, writes the target and affected files as one application-level batch, and publishes a new projection only after success. Fingerprint conflicts, incomplete projection, parse errors, or write failures prevent the operation; rollback failure is reported explicitly.
- `archive --dry-run` performs the same completeness, owner, child, relationship, and conflict checks, reports the target and every planned relationship removal, and writes nothing.
- Archive may affect items owned by other people; only the archived target's owner is checked. The result contains structured changed-item details. No independent archive/audit log is designed; Git diff/history remains the durable audit trail. Large batches require explicit resource protection and never silently truncate.

### Resolved projection, cache, and touch semantics

- Work-item Markdown files are the sole authority. Waymark v1 does not persist `.waymark/index.json` or another JSON index.
- A process may hold an in-memory static frontmatter projection containing parsed core/custom fields, source paths, fingerprints, parse diagnostics, and forward/reverse core relationship helpers. It is disposable and rebuilt from files; it is not a second source of truth.
- The projection does not persist `ready`, `blocked`, `blocked_by`, children, dependents, or relationship diagnostics as facts. These are dynamically computed from the current static projection.
- A complete fresh projection is required for global list/stats/tree/ready/blocked queries, Archive, and cross-file relationship writes. A scoped/local operation may read a file directly without loading it into the long-lived projection, but must identify itself as scoped/incomplete.
- `show <id>` may use a direct file read and may temporarily read related frontmatter without recursively loading the whole graph. A `load_into_memory` strategy controls whether a read updates the long-lived projection.
- Long-lived MCP/Web contexts may retain a projection. Each operation performs lightweight inventory checks; new, deleted, moved, or uncertain files invalidate the relevant entry or whole projection. CLI may build a projection for one invocation and discard it on exit.
- A bounded configurable LRU is allowed only for body, detail, or query-result performance caching. It is fingerprint-bound, cannot evict relationship nodes from a complete projection, and cannot weaken freshness, completeness, authorization, or archive rules.
- `touch` is an internal term for a Waymark-controlled frontmatter query, frontmatter mutation, or archive. It is not arbitrary body access and does not mean updating a timestamp. Public APIs use explicit read/write/archive/sync names.
- Waymark writes documents first under the project lock with optimistic fingerprint conflict detection, then synchronizes or rebuilds the projection. Incremental synchronization is allowed only when the affected scope is known; otherwise the complete projection is rebuilt. Partial projection state is never published as complete.

### Resolved body-editing semantics

- Body editing follows Clove's unified partial-edit contract: absent body input leaves the body unchanged; a present empty string clears it; a present non-empty string fully replaces it.
- v1 does not provide interactive `$EDITOR` editing. CLI supports non-interactive `--body TEXT` and `--body-file PATH` (mutually exclusive); MCP accepts structured body input and never launches an editor.
- Create and edit canonicalize a non-empty body to exactly one trailing newline without trimming leading or internal whitespace. Body content is not interpreted as a relationship language.
- Body and frontmatter changes are validated and written as one fingerprint-checked atomic document replacement. A real ordinary body change updates `updated_at`; an unchanged body produces no write. Archive remains the explicit exception and does not update `updated_at`.
- Body search reads body on demand and may use its own LRU. A stable ID appearing in body text is not a structured relationship and is not automatically diagnosed or rewritten.

### Resolved validation, diagnostics, and identity rules

- Stable IDs are immutable and project-unique: `wm-` plus 12 Crockford Base32 characters, persisted lowercase and accepted case-insensitively. Duplicate normalized IDs, case variants, ID/path mismatches, or multiple files for one ID are errors; projection must not choose one arbitrarily.
- `doctor` is diagnostic-only for business data. It may report source/fingerprint changes, new/deleted/moved files, duplicate IDs, parse/validation errors, missing or archived targets, cycles, path conflicts, and projection incompleteness, but does not delete relationships, modify body/custom fields, restore items, or infer user intent. Cache/projection rebuild is the only safe internal repair.
- Fingerprint validation uses path inventory, size, and mtime as cheap signals, then content fingerprint when needed. If metadata changes but content fingerprint is equal, the parsed projection may be retained after refreshing metadata; only content changes trigger semantic re-import.
- Local reads may succeed for valid files when another file is broken. Global graph queries, Archive, migration, and multi-target relationship writes require a complete projection and fail explicitly on parse errors or uncertainty.
- Machine metadata exposes source (`direct_file` or `memory_projection`), completeness (`scoped` or `complete`), freshness, and diagnostics so callers can distinguish local reads from complete graph results.

### Resolved query, relationship, and migration semantics

- Collection queries are active-only by default. `--archived` selects archived-only; there is no implicit active-plus-archived collection. `show <id>` is the explicit ID-read exception.
- Structured list/query uses frontmatter and custom fields and does not read body. `search` may read title, frontmatter, and body, uses a body cache if available, and follows the same active/archived range rules.
- Parent, dependency, and soft-link mutations use dedicated validated operations rather than arbitrary generic field patches. Multi-target requests prevalidate and commit atomically; self-links, duplicate edges, archived targets, invalid references, and cycles are rejected. Soft links remain symmetric.
- Parent and dependency cycles are rejected at write time; doctor diagnoses cycles introduced by external edits. Soft links are non-blocking and do not form lifecycle cycles.
- Category display-name changes do not move files. Category key changes and category storage-path changes require explicit migration/move operations with full prevalidation. Path overlap, target collision, and case-equivalent collision are diagnosed and never overwritten.
- Custom field keys use lowercase ASCII `snake_case`; core and computed names are reserved. Schema changes that can invalidate existing values require explicit migration; adding optional fields or changing display metadata can be direct. Migration never silently drops, guesses, or partially converts values.
- Query results use deterministic ordering, stable-ID tie breakers, and snapshot-local pagination. Missing custom-field sort values use the previously defined deterministic rule. Stats always states its active/archived range and projection completeness.
- Core frontmatter references are structured and managed by Waymark. Body text and custom-field values are not treated as references, even when they contain stable IDs.
- Creator is assigned at creation and is immutable provenance; owner is required, may initially differ from creator, and is the current accountability boundary. Owner transfer is initiated only by the current owner, takes effect immediately, updates `updated_at`, rejects empty/whitespace identities, and is forbidden for archived items. The previous owner loses mediated-write authority immediately.
- Status is exactly `open`, `in_progress`, or `closed`. Any explicit transition among these states is allowed for active items; status changes update `updated_at`, entering `closed` sets `closed_at`, leaving it clears `closed_at`, and repeating the same status changes nothing. `closed_at` is system-maintained; inconsistent external values are diagnostics. Archive never changes status or `closed_at`.
- Create generates stable ID, `created_at`, and `updated_at`; callers cannot provide them. Generic edit cannot change `id`, `creator`, or `created_at`; `closed_at` is maintained only by status transitions; archive metadata only by archive; relationships only by dedicated validated operations or archive cleanup. External violations are diagnosed, not silently repaired.
- Create may include initial parent, dependencies, and soft links. The complete request validates ID/category/targets, active target state, self-reference, duplicates, cycles, owner guardrails, and atomic persistence before writing; invalid initial relations fail the whole create.
- System timestamps are generated by Waymark rather than accepted from ordinary callers; production APIs do not permit user-forged `created_at`, `updated_at`, `closed_at`, or `archived_at`. The project configuration supports a declared time zone for human-readable rendering and interpretation of local time inputs without offsets, while persisted timestamps remain UTC RFC 3339. Offset-bearing inputs retain their instant; changing the configured time zone never rewrites work-item files.
- Every public operation checks configuration freshness. Storage-root, category-key/path, and custom-field-schema changes invalidate the current projection and require rediscovery/validation; operator changes immediately affect mediated-write checks; cache-only changes clear evictable LRU data without changing the static projection.
- Stable-ID filenames use the persisted lowercase ID plus a fixed Markdown extension. Title/display names never enter filenames; category path/key changes move files without changing IDs. Existing targets, case-equivalent collisions, path overlap, and ID/path mismatch are errors, never overwritten or title-inferred.
- Git checkout/revert/reset is interpreted entirely from current authoritative files. Fingerprint changes invalidate old projections; no hidden restore log or automatic repair of other files is maintained. Reintroduced archived targets or old relationships are diagnosed from current content.
- Unsupported future format/config versions can be reported for local reads while leaving other valid files locally readable, but make the project projection incomplete and prohibit migration, archive, global statistics, and cross-file relationship writes. Waymark never guesses, downgrades, discards unknown data, or silently repairs it.
- The project config declares a time zone for human-readable output and interpretation of time input that lacks an offset. Persisted `created_at`, `updated_at`, `closed_at`, and `archived_at` remain UTC RFC 3339 values; changing the configured time zone changes display/input interpretation only and does not rewrite work-item files or update business timestamps. Machine responses default to UTC and may include configured-zone display values where defined. Inputs that already carry an offset are not rewritten according to config timezone.
- Ordinary create/edit/status/archive operations generate system timestamps from Waymark's clock and do not accept caller-supplied system times. A separately specified historical migration/import path may transform legacy times, but ordinary user APIs cannot forge `created_at`, `updated_at`, `closed_at`, or `archived_at`; external invalid time values are diagnostics.
- The final external interface must expose both CLI and MCP over the same shared function library; core capabilities are defined by library functions rather than independently by either adapter. CLI and MCP receive the same v1 capability coverage and must enforce the same validation, ownership/operator, relationship, multi-document atomicity, concurrency, archive, migration, configuration, and diagnostic semantics. They may differ only in interaction and transport representation.
- Project-maintenance capabilities are not split by adapter: initialization, configuration inspection/validation, doctor, migration, projection synchronization, and Git history/diff access are all eligible for both CLI and MCP. Any safety behavior such as dry-run, complete prevalidation, and structured errors is shared rather than used to make MCP a weaker product surface.
- Configuration changes are also exposed through shared functions and both adapters, so configuration edits are versionable and reviewable through Waymark's normal deterministic file changes. Configuration updates must use structured operations with validation, conflict checks, and explicit migration handling when existing work-item data could be affected; there is no unrestricted raw configuration patch.
- CLI may expose convenience commands such as `start`, `close`, and `reopen` as adapters over the shared status operation; these are not separate domain capabilities. MCP should expose the structured status operation rather than requiring one tool per convenience alias.
- Waymark does not provide user-facing cross-work-item batch commands. Each write targets exactly one work item; CLI accepts no multiple IDs and MCP accepts no `items` arrays, and there is no arbitrary mixed-operation array. The all-or-nothing, per-target-outcome, and rollback rules apply only to a single operation that inherently writes multiple files — archive relationship cleanup, migration, multi-target relationship writes, and configuration/schema changes — and are provided by the shared write engine rather than by a batch API.
- Editing and migration contracts are both resolved in this map; what remains for them is naming and transport shape, tracked under Not yet specified.

### Resolved migration and versioning semantics

- The configuration version is written `major.minor`, meaning `format generation.configuration revision`. The major is the on-disk format generation: it is declared by the installed Waymark release and changes only when Waymark's own file format changes (core field set, serialization rules, or body rules). No configuration edit can raise the major.
- The minor is a monotonic configuration revision counter: it increments by exactly one when a Waymark-mediated configuration write actually changes configuration content, and does not increment for a no-op write. Direct hand edits of the configuration file do not move it. A version migration that also rewrites configuration counts as one configuration write.
- The minor is informational only. Freshness, projection invalidation, concurrency conflict detection, and cache invalidation are determined by file fingerprints, never by the revision counter; hand-edited configuration is detected by fingerprint regardless of the counter.
- `migrate version` accepts only a target format generation that the installed Waymark release can write; the user chooses when to run the migration, not which generation number to declare.
- Work-item frontmatter persists only the format generation. It never persists the configuration revision, so a configuration change can never make an existing work item stale.
- Migration has three kinds: version (format/compatibility generation), schema (project custom-field definitions), and storage (storage root, category key, or category path relocation). All three expose a `--dry-run` preview that performs the full read-only check and reports affected files, and a real execution that performs the same checks before writing.
- No persisted migration plan artifact is designed: there is no plan file, plan id, or plan/apply handshake. `--dry-run` plus re-derivation at execution time replaces it.
- Durable migration backups under `.waymark/` are not provided. Recovery after a successful-but-wrong migration relies on Git or user copies. A single migration run is still application-level all-or-nothing with in-run rollback from staged copies, and rollback failure is reported explicitly.
- Migration is permitted outside a Git repository, with a warning that a successful migration cannot then be recovered through Git.
- Schema migration covers only adding a custom field (no file rewrite; the field is simply unset on existing items) and removing a custom field (the key is deleted from every work item, including archived items). Changing a field's type, renaming a field, changing a list element type, or making an optional field required is rejected by migration and must be handled by the user as an explicit schema change plus a manual or scripted data edit.
- Because removing a declared field leaves existing files schema-invalid, that drift is detected by validation/diagnostics (undeclared key) rather than by any version comparison.
- A work item whose format generation is older than the configured generation is read-only for mediated writes: title/body/custom-field edits, status changes, owner transfers, relationship operations, and archive are rejected until an explicit version migration runs. Reads and `show` remain allowed, and list/tree/readiness/blocked/stats still include such items, marked as needing migration rather than hidden.
- Waymark retains a reader for the current and the immediately previous major generation; older generations are rejected as unsupported. This keeps the read-only window real while bounding parser maintenance.
- There is no separate compatibility-review command: `validate` and `doctor` perform the review against the current configuration, and `migrate <kind> --dry-run` previews the changes.
- The earlier "older data may be lazily upgraded on normal write" policy is withdrawn: ordinary writes never rewrite an older-generation file. Only an explicit migration changes a file's generation.
- Removing a custom-field declaration is a migration, not a configuration operation: there is no `config field remove`. Adding a field and changing display metadata remain configuration operations. This asymmetry is deliberate — adding is safe, removing has data consequences.
- `migrate schema --remove-field <key>` performs configuration removal and data removal as one application-level atomic operation: it removes the declaration, increments the configuration revision once, and deletes the key from every work item including archived ones. `--dry-run` reports the affected file list and count. A failure leaves both configuration and files unchanged.
- `migrate storage` is one command with mutually exclusive actions: `--root <path>` changes the storage root and moves every category directory; `--category-path <key>=<path>` changes one category's path and moves that directory; `--category-key <old>=<new>` changes one category's key and additionally rewrites the `category` value in every affected work item. Combining actions in one run is not supported.
- Storage migration prevalidation rejects, before any write: absolute paths or paths escaping the repository root; target paths that overlap any existing category path (equal, ancestor, or descendant); an existing non-empty target (never overwritten); a target that is case-equivalent to an existing path; symbolic links in the target path or any component it traverses; source files that do not exist, are unreadable, or disagree with the projection fingerprint; and an incomplete or stale project projection. Any failure aborts the whole migration and reports every diagnostic.
- Migration uses dedicated error codes because the recovery action differs: `MIGRATION_PATH_CONFLICT` for an existing, overlapping, or case-colliding target, `MIGRATION_UNSUPPORTED_GENERATION` when the installed release cannot write the requested format generation, and `MIGRATION_PRECONDITION_FAILED` for incomplete projections or fingerprint disagreement. Failures during execution remain `MIGRATION_FAILED` with per-target outcomes.
- The work-item title remains a core frontmatter field. The Markdown body is separate document content following Clove's frontmatter/body model; the title is not represented by a required Markdown level-one heading. Generic editing is divided by data area: title is the only core frontmatter field editable through the content-editing surface; custom fields are editable through their own custom-field surface; body is editable through a body surface. Other core fields are not generic-editable, even when they have dedicated domain operations (for example status, owner transfer, category move, and relationships); their values are system- or operation-managed rather than arbitrary frontmatter patches.
- The initial editing domain functions are `work_item_set_title`, `work_item_replace_body`, and `work_item_update_custom_fields`, with corresponding CLI surfaces `title set`, `body replace`, and `field update`, and corresponding MCP tools. Title is full replacement after trimming surrounding whitespace, must be non-empty and single-line, and has no patch/append semantics. Body is full replacement; an explicit empty string or empty body file clears it; non-empty body is canonicalized to exactly one trailing newline without trimming leading/internal whitespace. Custom-field updates use explicit per-field `set` or `clear`, allow multiple changes in one operation, reject `null`, unknown fields, set+clear conflicts, and clearing required fields, and validate the complete change set before writing. Each operation changes only its own data area plus `updated_at` when the effective value changes; unchanged requests do not write or update timestamps. CLI custom-field values use schema-aware parsing with canonical JSON literals for complex values and permitted simple scalar shorthand: strings may use an unambiguous token or JSON string literal, integers use decimal integer syntax, booleans accept only `true`/`false`, and lists require JSON arrays. A single `field update` may mix repeated `--set` and `--clear`; duplicate or set/clear-conflicting keys are rejected and the complete change set is validated before one write. MCP uses structured JSON values and explicit set/clear changes through a required `changes` map; each change is exactly set or clear, null is rejected, and required fields cannot be cleared. CLI body replacement uses direct `--body` or `--body-file` input, with no interactive editor in v1; MCP never launches an editor. The three edit tools return the complete resulting work item plus `changed`; custom-field updates also return `changed_fields`. All three editing operations require the declared operator to match the current owner, reject archived items, use fingerprint conflict detection, and perform one atomic document replacement per target; unchanged effective values do not write or update `updated_at`. CLI supports human and versioned JSON output, while MCP returns the shared versioned envelope. Editing is single-target: there is no batch variant, no implicit multi-ID form, and no mixed-operation array. Exact transport schemas remain under editing-contract review.

### Resolved write-lock lifecycle

- The project write lock is one store-wide advisory lock on a dedicated file at `<project>/.waymark/write.lock`. It is never taken on a work-item file: those are replaced by temp+rename, so an advisory lock on one binds to an inode that is no longer the item's path.
- It is an OS advisory exclusive lock (`flock`/`fcntl` on Unix) held on an open descriptor for the operation's whole read-modify-write window, released by the kernel when the process exits or crashes. There is no stale-lock reclamation, no PID probe, no mtime expiry, and no holder metadata: the lock file's content is never read or written.
- The lock file is created by the first mediated write, and it is listed in `.waymark/.gitignore`; a missing entry is repaired on the next lock acquisition. It is opened without following a symlink and must be a regular file, so a cloned repository cannot turn it into a link to a user file.
- The lock is non-reentrant. One public operation acquires it exactly once and holds it through prevalidation, every write it stages, and rollback; internal helpers that write receive the held guard instead of acquiring again, and nested acquisition is a programming error rather than a wait.
- Every mediated write takes this one lock — work items, relationships, archive, migration, and configuration edits. Reads, `show`, dry-runs, and previews never block on it; a global read builds its projection and detects a concurrent multi-file write through its inventory/fingerprint check, retries a bounded number of times, then returns a retryable error rather than a torn snapshot.
- Long-lived adapters never hold the lock between calls: the MCP server and Web each acquire it per mediated write and release it before responding.
- A writer waits a bounded time for the lock, 10 seconds by default, configurable per project and overridable per operation through a shared option exposed by both CLI and MCP (`0` fails immediately). On expiry it returns a retryable structured error naming the lock path and waited duration and guaranteeing that nothing was written; no holder identity is exposed.
- Failing to open or take the lock file (unreadable path, read-only project directory, a non-regular file) is a terminal operation error. Reads keep working in a read-only checkout because they never need the lock.
- Concurrency failures stay three distinct conditions: lock contention (retryable, nothing written), a fingerprint conflict with an external edit (terminal; the caller must reread), and reader snapshot instability during a concurrent multi-file write (retryable, read-only). Only their code names wait on the error-taxonomy ticket.
- `doctor` probes the lock with a non-blocking try-lock and, when it is held, reports a non-fixable informational finding that a mediated write is in progress; it never waits and never reports a holder identity.
- The lock's lifetime follows the project metadata directory, not the storage root: storage migration never moves or recreates it.
- v1 targets Unix (Linux and macOS). Advisory locking, `O_NOFOLLOW`, and temp+rename replacement are specified against POSIX semantics; Windows support is explicitly out of scope instead of being implicitly assumed. The lock covers local filesystems only; concurrent access over NFS/SMB is not supported.

### Resolved error taxonomy structure

- One shared registry is the single classification source. Each entry records the stable code, its exit class (2–7; class 1 stays adapter-level), whether the same request is retryable, the typed details shape, the location kinds it may carry, and whether the code may also appear as a diagnostic finding. The CLI exit mapping and the MCP business-error representation both read this registry; neither adapter keeps its own match.
- Codes are flat `SCREAMING_SNAKE` strings. Their names carry no parsed semantics: exit class and retryability are registry attributes, never derived from a prefix. `MIGRATION_*` remains a naming convention, not a classification rule.
- A code names a recovery unit, not an error variant. A new code is warranted only when the recovery action differs; when only the offending value differs, the difference belongs in typed details. Following Clove's precedent, `PARSE_ERROR` and `VALIDATION_ERROR` deliberately cover whole families of conditions instead of one code per condition.
- Choices that follow from that rule: `CYCLE_DETECTED` covers both dependency and parent cycles, with the kind in details; `INVALID_RELATIONSHIP` covers self-reference, duplicate edges, and wrong relation kinds, with the reason in details; `VALIDATION_ERROR` covers field type mismatch, missing required field, unknown field, empty or multi-line title, invalid status literal, `set`/`clear` conflicts, and `null` values, with a per-field issue list.
- Every error carries `{v, code, message, details, location?, retryable}`. Details are typed per code rather than a free-form map, and location is a tagged union over `work_item`, `file`, `field`, `config_key`, and `relationship`. Messages stay human-readable and are never parsed for classification.
- Diagnostic findings reuse the same registry instead of defining a second vocabulary: `{severity: error|warning|info, code, location?, message, fixable}`. `validate --strict` maps remaining error-severity findings to exit class 3; `doctor` reports the held-lock probe as an info-level, non-fixable finding.
- The exit class is a registry attribute read by both adapters. Class 4 is narrowed to conflict and state rejection (write conflict, archived target, archived item write, active children); rejecting a write to a stale-generation item is class 6; an incomplete projection is class 3; lock contention and an unstable reader snapshot are class 5. Warnings never change the exit code.
- Usage-level failures stay adapter-level: bad flags and unknown subcommands exit 1 with `USAGE_ERROR` and are not part of the domain registry. MCP JSON-RPC protocol errors stay separate from business errors.
- Advisory operator/owner mismatches are warnings, carried in `_meta.warnings` as `{code, message, location}` entries with a registry code such as `OWNER_MISMATCH`, and never produce a non-zero exit.
- In JSON mode the failure envelope `{v, ok: false, error}` is written to stdout, so a parser always receives valid JSON; stderr stays human narrative.
- The registry is pinned four ways: a wildcard-free compile-time match forces every error variant to declare a code; a registry-consistency test keeps the code table and that match in step; a JSON-schema enum round-trip keeps the documented schema honest; and a golden snapshot records each code's exit class, retryability, details keys, and location kinds. Adding, removing, or re-classifying a code therefore requires updating the snapshot and the documented table in the same change.

### Resolved error registry

Class 2, not found: `ITEM_NOT_FOUND {id, relation?}` and `CATEGORY_NOT_FOUND {key}`. Neither is a finding.

Class 3, invalid input or data: `VALIDATION_ERROR {target, issues:[{path, reason}]}` (finding), `INVALID_ID {value, reason}`, `PARSE_ERROR {path, reason}` (finding), `CONFIG_INVALID {path, issues[]}` (finding), `DUPLICATE_ID {id, paths[]}` (finding), `ID_PATH_MISMATCH {id, path, stem}` (finding), `CYCLE_DETECTED {kind: dependency or parent, cycle[]}` (finding), `INVALID_RELATIONSHIP {relation, from, to, reason}`, and `INCOMPLETE_PROJECTION {completeness, freshness, diagnostics[]}` (finding).

Class 4, conflict or state rejection: `WRITE_CONFLICT {id, path, expected_fingerprint, actual_fingerprint}`, `ITEM_ARCHIVED {id, operation}`, `ALREADY_ARCHIVED {id}`, and `HAS_ACTIVE_CHILDREN {id, children[]}`. None is a finding.

Class 5, filesystem, Git, or environment: `PROJECT_NOT_FOUND {searched}`, `IO_ERROR {path, operation}` (finding), `GIT_ERROR {operation, reason}`, `LOCK_TIMEOUT {lock_path, waited_ms}` (retryable), `LOCK_FAILED {lock_path, reason}`, and `SNAPSHOT_UNSTABLE {retries}` (retryable).

Class 6, version or migration: `UNSUPPORTED_VERSION {found, supported}` (finding), `ITEM_NEEDS_MIGRATION {id, item_generation, project_generation}` (finding), `ACTION_REQUIRES_MIGRATION {action, required_command}`, `MIGRATION_PATH_CONFLICT {target, conflict}`, `MIGRATION_UNSUPPORTED_GENERATION {requested, supported}`, `MIGRATION_PRECONDITION_FAILED {diagnostics[]}`, and `MIGRATION_FAILED {per_target:[{path, outcome, error?}]}`.

Class 7, internal: `ROLLBACK_FAILED {applied[], failed[], rollback_failed[]}`, `ID_GENERATION_FAILED {attempts}`, and `INTERNAL_ERROR {}`.

Codes with no exit class, used as warnings and findings: `OWNER_MISMATCH` (warning, `{item, operator, owner}`), `LOCK_HELD` (info, `{lock_path}`), `MIGRATION_AVAILABLE` (info, `{items[]}`), `NOT_A_GIT_REPOSITORY` (info, `{}`), `DANGLING_REFERENCE` (error-severity finding, `{from, relation, missing[]}`), and `TIMESTAMP_INCOHERENT` (warning finding, `{id, field, value, reason}`).

`LOCK_TIMEOUT` and `SNAPSHOT_UNSTABLE` are the only retryable codes; every other code is terminal. `USAGE_ERROR` at exit 1 is an adapter-level failure and is deliberately absent from the registry.

### Reopened decisions: Web, MCP, and distribution

The following decisions extend the accepted specification. The Web implementation and behavior decisions have been synchronized to `wm-srxj8ztv1zfz` and T12 (`wm-a22prtcw8kda`); the MCP and formal distribution decisions and their implementation tickets have not yet been synchronized.

- Use existing frameworks for the Web HTTP service and for MCP, rather than implementing HTTP or the MCP protocol by hand. Clove is technical prior art, not a requirement to copy its product scope or response contracts.
- MCP prefers rmcp with Tokio; select its version and features only after verifying the complete dependency graph against the supported Rust version. First investigate compatible rmcp versions or feature combinations under Rust 1.85. If no suitable option exists, assess raising the minimum supported Rust version and report the trade-off for a decision; do not silently raise it or assume Rust 1.88 is sufficient for the complete dependency graph.
- MCP initially uses stdio: a local MCP client starts the Waymark server process and communicates over standard input/output. An HTTP MCP transport is not part of the initial choice. Web HTTP remains a separate interface. MCP must preserve Waymark's shared business rules, versioned envelopes, and typed errors rather than copying Clove's different MCP result format.
- The Web backend uses Axum and Tokio; the Web frontend uses SvelteKit, Svelte, TypeScript, and Vite. Select compatible versions after validating the complete dependency graph against the project's declared Rust version; report incompatibilities rather than silently raising that version. Web remains strictly read-only and does not acquire Clove's other product features by virtue of this stack choice.
- The basic distribution includes CLI, the shared core, and MCP; Web is optional. A build-time feature selects Web: the default build is the basic version, while a Web-enabled build includes Web. Adding Web to an installed basic executable requires rebuilding or installing a Web-enabled replacement, not dynamically attaching a module. Exact artifact names and packaging details remain open.
- The basic CLI retains `waymark serve` but reports clearly that Web is not included and directs the user to install a Web-enabled build; it never downloads or installs anything automatically.
- A Web-enabled build must obtain complete frontend assets. Missing assets or a frontend build failure must produce a clear build failure, rather than silently shipping a placeholder or stale frontend as a successful Web build.
- A prebuilt Web-enabled binary includes its frontend assets; an end user running it does not need Rust, Node.js, or npm. To build the frontend from source, the developer needs Node.js and npm unless verified prebuilt assets are supplied instead.
- Formal releases provide separately named prebuilt basic and Web-enabled binary packages. Both identify their version and included capabilities; the basic package includes CLI and MCP without Web, and the Web package includes those capabilities plus Web.

The published Web source package instead includes prebuilt frontend assets, avoiding a GitHub Release download at build time. These assets must correspond to the source version and release checks must validate that correspondence. The exact verification mechanism remains open. Both paths embed assets in the resulting binary; Web runtime requires no Node.js/npm.
- The first Web version listens only on local loopback addresses; it offers no LAN or public network binding option. Render work-item titles and bodies safely so project content cannot execute as page script. - Persist selected view, per-view expansion, dependency visibility and scroll position in the browser only, separated per Waymark project at a given local service origin. Opening two projects on the same origin in the same browser must not overwrite the other project's view state. Browser storage is origin-scoped: a different port, host, scheme or browser may start with default state, with no shared service or project file for synchronization. Use a local identifier derived from the normalized project-root path to isolate projects on that origin; moving a project to another path creates a new browser-state identity and starts from defaults.
